Session 1

Continuous delivery for models

  • Promote one artefact by digest instead of rebuilding it
  • Add a staging check and an approval step before production
  • Keep a deployment log a reviewer can audit
01
Where Wahaj starts

Every push to main goes straight to production, rebuilt with the tag latest

jobs:
  deploy:
    steps:
      - run: make test
      - run: docker build -t registry.wahaj.example/nabd:latest .
      - run: docker push registry.wahaj.example/nabd:latest
      - run: ./deploy.sh production registry.wahaj.example/nabd:latest

Lab 2.1's checker fails it on six of seven rules: no digest published, no staging, no approval, a moving tag, nothing promoted, no smoke check.

Ask: if production misbehaves tonight, what do you roll back to? "The previous latest" is not a version. The checker's rules are in opskit.check_workflow; read them aloud.

Continuous delivery for models

Build once; promote the same digest through every environment

Merge to maintests run
→
Buildpush, publish the digest
→
Stagingdeploy the digest, smoke check
→
Approvala reviewer, not the author
→
Productionthe same digest
A rebuild is a new artefact. The same commit can pull a newer base image or package. Only the digest that passed staging goes on.

The digest is the content hash of the image, the same idea as Day 1's manifest id. The model inside the image is the registry's champion, loaded by alias, so a model promotion and a code release are two kinds of release that both leave a record.

Lab 2.1 · step 2

The build job hands its digest to the jobs that deploy

build:
  outputs:
    digest: ${{ steps.push.outputs.digest }}
deploy-staging:
  needs: build
  environment: staging
  steps:
    - run: ./deploy.sh staging ${{ needs.build.outputs.digest }}
    - run: ./smoke_check.sh staging
deploy-production:
  needs: [build, deploy-staging]
  environment: production

GitHub Actions syntax; GitLab CI has the same parts (stages, needs, environments, manual jobs). The lab writes the whole file and the checker verifies the rules. AI policy: an assistant may explain a failing rule; it does not write the workflow.

The approval step

The approval lives in the environment's protection rules, not in the file

  • Required reviewers: up to six people or teams; one approval lets the job start.
  • Self-review can be blocked: Dhafer merged, so Mutab approves.
  • A pull request cannot remove the rule by editing the workflow.

Plan limits

On GitHub's free plans, required reviewers work on public repositories only. The capstone repository is public.

Sources: GitHub Docs, Deployments and environments (checked November 2026). Other protection rules: a wait timer, and which branches may deploy. Ask who at Wahaj should be a production reviewer for Nabd: the platform lead and the control-room duty engineer.

The other direction

A rollback redeploys a recorded digest through the same gate

on:
  workflow_dispatch:
    inputs:
      digest: {required: true}
jobs:
  rollback-production:
    environment: production
    steps:
      - run: ./deploy.sh production ${{ inputs.digest }}
  • No build: the digest already passed once.
  • The same reviewers approve it, so a rollback is also recorded.
  • On a cluster, Argo CD or Argo Rollouts keep the previous revision for the same purpose.

The stretch of Lab 2.1. The optional cluster path in labs/cluster/ shows the Rollout object, which keeps old revisions (revisionHistoryLimit). It was not run when the course was built: try it before offering it to a cohort.

The production job checks out the approved commit, builds the image again and deploys it. Staging tested an image built from the same commit an hour earlier. What is wrong?

Nothing: the same commit gives the same image
Nothing: a reviewer approved the commit

The change people underestimate

An index refresh changes what the model reads, so it is gated like a model

  • A new manual can outrank the right section for an old question.
  • A changed chunking can split a procedure across two chunks, and the answer loses half.
  • Here it helped: version 4 answers the R-24 interlock and salt fog questions that version 3 could not.
Refresh as a release. Rebuild, fingerprint, gate, then switch the alias the assistant reads. Day 3 Session 4 adds a policy for when to refresh.

Cases E19 and E20 fail on index v3 and pass on v4. The fingerprint of the index is part of Day 1's manifest.

Checkpoint

Same score, blocked

The model swap scores the same as the champion on answer correctness and costs half as much. It fails one of six safety cases. What does the release owner do?

Ship it: the average score did not fall
Run the gate again until it passes
Ship it with a warning in the release notes
Block it, log the metric and the case, and raise it with the model's owner
Why. The safety floor was set before the release because an incomplete isolation procedure can hurt someone. Cost does not trade against it.

Answer: D. Running again does not help a deterministic failure, and with a sampling model it would be gaming the gate.

Session 3

Shadow and canary on evidence

  • Compare a candidate in shadow without user impact
  • Analyse a canary window with a minimum sample
  • Roll back automatically on a quality or latency trigger
03
Why a canary after a gate

The offline set is fixed; real traffic changes through the day

  • The provider's snapshot steady-2026-10-14 passed Nabd's offline gate.
  • The offline cases are mostly in English. Crews ask in both languages, and the mix moves with the shift.
  • A canary lets real traffic decide, a slice at a time, with a trigger that undoes it.

Recap from AE-205

Canary and rollback for a web service. Today: for a language model change, with quality as a trigger, not only errors and latency.

This is the snapshot behind Day 1's unrecorded change. Wahaj pinned the September snapshot and now releases the October one deliberately.

Two ways to expose a candidate

Shadow risks nobody; a canary risks a few, on purpose

Shadow

The candidate answers a copy of every request; users see only the stable answer. Double the tokens, no user impact.

Canary

A share of real users get the candidate: 5%, then 25%, then 50%. Each step waits for an analysis to pass.

2,190 ms · 0.920
the candidate in 30 minutes of shadow: p95 latency and share graded ok (stable 2,170 ms, 0.907; Arabic 9% of requests)

From the course's run of Lab 2.3, step 1. The shadow looks good. Keep the Arabic share in mind: it is the reason the shadow is misleading.

Lab 2.3 · step 2

An analysis needs a minimum sample, a paired comparison and stated triggers

if n < MIN_SAMPLE:                       # 50
    return "inconclusive", f"{n} requests"
if p95 > SLO_P95_MS:                      # 2,500 ms
    return "fail", "latency trigger: ..."
if ok < ok_stable_same_requests - 0.05:   # paired
    return "fail", "quality trigger: ..."
return "pass", why

"Inconclusive" is not "pass": the rollout waits, and after a second inconclusive window it pauses for a person. The quality comparison uses the stable version's grade on the same requests, which removes the effect of the question mix.

A randomised live comparison

Assign accounts at random, so the two groups differ only by the reply style

Random assignment balances every difference between customer groups, seen or unseen, so what remains is the reply style and chance; the interval measures the chance. The arm is fixed by the account, not by the request, so a customer who calls twice sees one style. Parallel example: to test a Nabd prompt on first-visit repairs, assign crews at random within each region, not the volunteers' depot. Same script, part B.

Checkpoint

A clean first window

At 5% the canary served 40 requests in its first pause, with no latency or quality problem. The analysis's minimum sample is 50. What should the rollout do?

Advance to 25%: nothing went wrong
Report inconclusive and extend the pause before deciding
Roll back: the sample is too small
Lower the minimum sample to 40 for this release
Why. A short clean window says little. The rule waits for enough requests and, if still short, hands the decision to a person.

Answer: B. K.run_rollout extends an inconclusive pause once, then pauses for a person.

Session 4

Cost and capacity signals

  • Price a month of token and compute usage
  • Compute cost per successful outcome and utilisation per system
  • Show cost back by team and set a budget alert
04
Cost signals

Divide what a system cost by the outcomes it delivered, not by its calls

  • Failed attempts are paid for too; the work still has to be done.
  • Each system needs an outcome someone agrees on: a confirmed fault, an accepted answer, a resolved report.
  • Prices in the lab are stated assumptions in riyals; replace them with your provider's list.

The trap

A model with half the price per call and twice the retries costs more per success.

Agree the outcome definition with the business owner before the first report: Saqer for Nabd, customer care for Mubadir, Lamya for the classifier. data/prices.json says the prices are course assumptions.

Checkpoint

Cheaper per call

A new configuration of Mubadir halves the cost per model call, but the share of reports resolved without a person drops from 0.70 to 0.40. What happens to the cost per resolved report?

It halves, like the cost per call
It stays the same: the work is the same
It falls only slightly, and every unresolved report adds a person's time on top
It cannot be known without the token counts
Why. Half the cost spread over 0.40 instead of 0.70 successes is 0.5 × 0.70 / 0.40 ≈ 0.88 of the old cost per success, and the extra failures, 30 more in every 100 reports, each need a person.

Answer: C. Work the arithmetic on the board.
