A hand-kept version number changes when someone remembers to bump it. A content hash changes whenever anything changes, including what nobody thought about. Line endings are normalised before hashing so that a Windows and a Linux checkout agree; ask the room why that matters.

Data versioning

Name the data by its content, as DVC and lakeFS do

data = df.to_csv(index=False).encode()
h = sha256(data)
path = store / h[:2] / f"{h}.csv"
if not path.exists():
    path.write_bytes(data)
  • The same rows give the same name on any machine.
  • A file called training_latest.csv says nothing about which rows it held last month.
  • The tools add remote storage, branches and garbage collection; the idea is this one line.

DVC keeps files in a content-addressed cache and lets git track the small pointer files; lakeFS gives a data lake commits and branches. Both are examples of the slot; the lab uses the bare idea so it runs anywhere.

A trap in Lab 1.2

Parameters come back from the tracking store as text

MLflow logs parameters as strings. "4" as a sample weight raises an error; a "False" string is truthy. Lab 1.2 has a NUMERIC map for this.

What lineage still misses

The library versions are part of the release too

  • The same code and data on another scikit-learn version can give different trees.
  • labs/uv.lock pins every package; the capstone repository commits its own lock file.
  • A container image digest pins the operating system and Python as well (AE-205).
In Colab the libraries are Colab's, so a rebuild there can differ from your laptop's by a few thousandths: that difference is an environment change, and now you can name it.

Data contracts

A contract says what every row and every batch must be

Row rules

Types, patterns (^F-\d{4}$), allowed values, physical ranges (load 20 to 150 percent of rating), no nulls.

Batch rules

One row per feeder, every feeder present (within 2%), the month the file claims.

Agree it with the data owner. The SCADA export team signs the contract; your pipeline enforces it on every delivery.

The contract is a shared promise, not a private check: the report goes back to the owner of the source. The ranges are physical limits agreed with engineering, not statistics of last month.

The contract as a pandera schema

import pandera.pandas as pa
SCHEMA = pa.DataFrameSchema({
    "feeder_id": pa.Column(str, pa.Check.str_matches(r"^F-\d{4}$")),
    "region": pa.Column(str, pa.Check.isin(["RIM", "HAD", "SAH", "WAD", "JAB", "NAK"])),
    "load_peak_pct": pa.Column(float, pa.Check.in_range(20, 150)),
    "fault_30d": pa.Column(int, pa.Check.isin([0, 1])),
    ...
}, strict=True)
SCHEMA.validate(df, lazy=True)   # every failure, not the first

pandera is one example of the validation slot; recent versions import the pandas API from pandera.pandas. strict=True also fails on an unexpected column. lazy=True collects every failure into one report: the data owner fixes all of them in one delivery.

What the pipeline must not do

Report the fault to the owner; do not quietly repair it

Quiet repairs

Dropping duplicates, multiplying small loads by 100, stripping spaces: each hides a broken export that will break again.

Stop, quarantine, report

Keep the failing rows apart, send the counts and one example, retrain when the corrected batch arrives.

The stretch writes the quarantine file and the three-line report. Ask: who decides that a load of 0.86 means 86 percent? The data owner, not the pipeline.

Lab 1.4 · step 4

Promotion moves an alias, and the old champion stays one move away

old = client.get_model_version_by_alias("fault-risk", "champion").version
new = client.get_model_version_by_alias("fault-risk", "challenger-b").version
client.set_registered_model_alias("fault-risk", "previous-champion", old)
client.set_registered_model_alias("fault-risk", "champion", new)
client.set_model_version_tag("fault-risk", new, "promoted_reason",
    "passed overall and in every region (holdout 2026-08, tolerance 0.03)")

Serving loads models:/fault-risk@champion, so this is the release. A rollback is the same call with the versions swapped. The reason tag is the audit record the entry asks for: every release decision is logged.

The tolerance

A rule with no tolerance rejects every challenger on noise

  • 200 holdout feeders per region, 16 to 81 of them with a fault in August.
  • Resample them and a region's AUC moves by a few hundredths.
  • Challenger B is at most 0.006 worse in any region (Al-Jabal): noise. A is 0.069 worse there: not noise.
Stretch. Bootstrap the Al-Wadi gap of challenger B and read whether its interval includes zero.

Set the tolerance from a bootstrap on your own holdout, write it into the gate, and do not change it during a release because a candidate fails by a little: that is how gates erode.
