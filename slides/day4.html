The agent

Mubadir is a model in a loop that reads a report, calls tools and writes tickets

Report"no power, account ACC-…"
→
find_customerfeeder, region
→
get_outageactive, restored, pending, none
→
Writelink, open a ticket and notify, or close

Each turn the model returns one JSON action; the harness runs it through the services and logs every event.

The services are SQLite files, so tickets survive a crash as they would in production. The model is the scripted stand-in when no key works; it follows the prompt's procedure and trusts whatever the outage service says.

Three things people mix up

The harness runs the loop, the sandbox limits it, the session log records it

Harness

Steps, retries, timeouts, guards: harness.yaml and its code.

Sandbox

Allowed tools, readable fields, no network: sandbox.yaml.

Session log

What one session did. Produced by a run, never released.

Ask where "never read out a phone number" lives. It is in the prompt and in the sandbox's hidden fields: the prompt asks, the sandbox enforces.

What reached Dhafer this month

A crew sent twice to one feeder, and a session that started again from the beginning

Restart

A deployment restarted the pod between creating the ticket and notifying the crew. The session started over and opened a second ticket.

Retry

The ticket service committed, then timed out. The harness retried and wrote again.

Two different causes with the same symptom. The fixes are different too: a checkpoint for the first, an idempotency key for the second.

Durable execution

A checkpointer saves the state after every step, under a thread id

g = StateGraph(Ticket)
g.add_node("find_customer", find_customer)   # ... get_outage, create_ticket, notify_crew
g.add_edge(START, "find_customer")
graph = g.compile(checkpointer=SqliteSaver(sqlite3.connect("checkpoints.db")))

graph.invoke({"account": "ACC-40000137"}, {"configurable": {"thread_id": "S-4202"}})
graph.invoke(None, {"configurable": {"thread_id": "S-4202"}})   # resume after a crash

LangGraph with the SQLite checkpointer runs on a laptop; in production the Postgres checkpointer or a durable execution engine plays the same part. Invoking with None on the same thread resumes from the last saved step.

Lab 4.2 · step 3

A timeout does not say whether the write happened

create_ticketthe service commits OT-31001
timeoutticket service did not answer within 5 s
retrycreate_ticket → OT-31002
notify_crewOT-31002 · OT-31001 is never notified

A checkpoint does not help here: the retry happens inside one step. Only the service can recognise the repeat, and it needs a key to do it.

Lab 4.2 · step 4

An idempotency key names one intended write; a repeat returns the first result

key = hash(session_id, "create_ticket", args)
# same intent, same key, on every retry
# a different report gets a different key
timeoutafter the commit
retryOT-31001, replayed: true
ticketsone, notified

Not the time of the call: a retry a second later would get a new key. Many payment APIs work the same way, with an idempotency key sent on each request. Every write tool needs one: create_ticket, notify_crew, close_report, update_customer_record.

Which fix for which failure

Checkpoints protect the steps between calls; keys protect the call itself

Checkpoint

The process dies between steps. Resume from the saved state; finished steps do not run again.

Idempotency key

The answer to one write is lost. Retry with the same key; the service does not write twice.

Both, for every agent that writes. The capstone's agent incident is a duplicate write.

Stretch: a second process reads the crashed thread's state from SQLite and sees the ticket it already holds.

Checkpoint

Checkpointed, still duplicated

Mubadir's flow now has a checkpointer. A ticket service timeout still produced two tickets for one report. Why?

The checkpointer was not saving
The ticket database lost the first ticket
The retry ran inside one step, and the service had no key to recognise it
The model asked for two tickets
Why. The service committed and its answer was lost; only an idempotency key lets it return the first ticket.

Answer: C.

Usual problems: invoking with the original input instead of None, which starts over on the same thread; a new thread id on resume; an idempotency key that includes the time. Delete artifacts/D4_2 between attempts: the ticket services are files.

Lab 4.3 · step 2

Replay from the recording, not a rerun against today's services

  • The recording holds every model output and every tool response.
  • Replay feeds them back through today's harness code: no model, no services.
  • The same wrong answer comes back every time.

A rerun would not

The replica has caught up and a hosted model can answer differently: the failure would hide.

This is why the session log keeps the tool results and not only the model's text, and why it is redacted and retained under the rules of Day 3 Session 3.

Lab 4.3 · step 3

A guard in the harness blocks a close on a stale status

def freshness_guard(action, history):
    if action["tool"] != "close_report":
        return None
    last = latest get_outage result in history
    if last["status"] != "restored":
        return "not restored"
    if last["age_minutes"] > 15:
        return f"status is {last['age_minutes']} minutes old: confirm with the control room"

Replayed with the guard: blocked at step 3, "status is 140 minutes old (limit 15)".

A guard runs on every call and is tested by replay; a prompt instruction is followed most of the time. The 15 minutes is the course's assumption: set it with the control room.

Stretch · the suite against a new bundle

A bundle without close_report changes exactly one case, as intended

  • The sandbox no longer allows close_report: closing goes to a person.
  • Replayed suite: "restored 6 minutes ago" now fails, everything else passes.
  • Update that case's expectation in the same change, with the reason.

A suite that changes is fine when the change is the one the release intends, and written down. An unexplained change is a regression.

Lab 4.4 · step 2

Every model call passes the gateway, which checks steps, session spend and the day's budget

def policy(state):
    if state["session_steps"] >= 12:      return "step limit"
    if state["session_spend"] >= 0.01:    return "session spend limit"
    if state["day_spend"] >= 2.90:        return "daily budget"   # 90 SAR / 31 days

The same runaway session: stopped by the gateway after 12 calls, 0.0057 SAR.

Why at the gateway and not only in max_steps: the gateway sees every session of every version, including a harness with a bug or a bundle that raised its limit, and it sees the money.

Lab 4.4 · step 4

Stopping the agent must not drop the customers it was serving

  • Every session is in the store with its messages and status.
  • Six stopped sessions go to customer care with the account, steps, spend and last tool result.
  • The same sessions can be replayed for the post-incident note.
6 of 6
stopped sessions handed over, none lost

The handover file holds the account number but no phone number or name: customer care looks them up in its own system.

Stretch · the same limits in a proxy

Six sessions looping

Stop all of Mubadir, every version
